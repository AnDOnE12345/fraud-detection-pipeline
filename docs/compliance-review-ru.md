# Проверка соответствия проекта условиям Cloud Computing und Big Data

> Исторический аудит версии `ebc3914`, до исправлений. Текущее устройство и статус проверки описаны в README; перечисленные ниже замечания не являются повторным аудитом изменённого кода.

Проект в значительной степени соответствует содержательным требованиям задания: реализованы ingestion, обработка потока, Lakehouse, serving и отдельная пользовательская UI; README содержит все 12 обязательных разделов. Однако полное соответствие пока не подтверждено. Основные препятствия: доказательства работоспособности противоречат подписи в README, масштабирование всех компонентов не реализовано и не показано, а агрегаты обработчика некорректны при нескольких экземплярах или потере состояния. Требование касается учебного прототипа, поэтому отсутствие промышленной отказоустойчивости само по себе не является причиной отрицательной оценки.[^1]

Проверяемая версия: рабочая копия репозитория на 8 сентября 2026 года, HEAD `ebc3914`. Git показывает изменения в 32 существующих файлах, но сравнение с игнорированием различий конца строки не показывает содержательных изменений. Сам по себе такой статус не свидетельствует о незавершённой функциональной работе. Оценка ниже относится к содержимому файлов и имеющимся доказательствам, а не к работающему кластеру.

## 1. Что именно требует задание

На странице 1 задания разрешены синтетические данные, альтернативные streaming engines, MinIO/S3 вместо HDFS и другие обоснованные технологические отклонения. Spark, HDFS, машинное обучение, реальные банковские данные и exactly-once не являются обязательными. Kappa указана как стандартная архитектура; выбранный проектом подход допустим.[^1]

На странице 2 отдельно требуется горизонтальная масштабируемость **всех компонентов** и её демонстрация. Формулировка не ограничивает это требование stateless-сервисами. Указание в README, что распределённые Kafka и MinIO оставлены на будущее, честно описывает границы, но не заменяет выполнение этого условия.[^1]

Проверяющий не будет запускать приложение и не будет скачивать внешние материалы. Оценивается единственный ZIP с README, исходниками, deployment-файлами, данными и встроенными изображениями. README является единственным отчётным документом; отсутствие обязательного раздела приводит к нулю в соответствующем критерии. В этом проекте все разделы есть. Настоящий аудит служит рабочим документом: необходимые изменения для сдачи следует внести непосредственно в README и соответствующие файлы.[^1]

## 3. Самые существенные замечания перед сдачей

### P1. Скриншот кластера не подтверждает исправную систему

В README §11, строка 324, написано, что все основные компоненты запущены. На [pods.png](screenshots/pods.png) видны `processor … 0/1 Error` и `producer … 0/1 Error`; serving и UI находятся в `Running`, но также имеют readiness `0/1`. Только Kafka и MinIO показаны как `1/1`. Это прямое противоречие между подписью и доказательством.[^7]

Изображение могло быть снято во время перезапуска; по нему нельзя установить причину ошибки или нынешнее состояние приложения. Но именно приложенные изображения заменяют функциональную проверку по правилам задания. Необходимо получить новый реальный снимок после устранения ошибок: все шесть основных workloads должны быть готовы, затем в том же запуске показать отправку события и появление результата. Менять пиксели состояния или лишь переписывать подпись недостаточно.

### P1. Масштабирование не закрывает прямое условие задания

На [scaling.png](screenshots/scaling.png) показаны HPA с CPU 4%, 56% и 5% при целевом значении 70%. Во всех трёх строках `REPLICAS=1`. Это подтверждает существование HPA и доступность метрик, но не демонстрирует увеличение числа экземпляров.[^7]

Для Kafka параметр replicas есть, однако каждый pod запускается с одним `--node-id=0` и общим advertised address `kafka:9092`. Нет конфигурации, обеспечивающей корректный многоброкерный кластер. Простое увеличение replicas не решает задачу. Для MinIO жёстко задана одна реплика и запуск `server /data`, без распределённой топологии. KEDA допускает до шести processor, но конфигурация по умолчанию его отключает, а сама обработка не сохраняет корректность при scale-out.[^6]

Чтобы устранить несоответствие, нужны работающий вариант многоброкерной конфигурации, распределённого object storage и корректного состояния обработки, плюс реальные доказательства работы компонентов в нескольких экземплярах. Для stateless-сервисов стоит приложить до/после: число pod, нагрузку, решение HPA и успешные запросы. Для инфраструктуры допустима отдельная конфигурация демонстрации, если она включена в ZIP, воспроизводима и описана в README. Одна схема предполагаемого production-развёртывания этого не подтверждает.

### P1. Category aggregates теряют часть данных при нескольких processor

`stats_state` находится в памяти отдельного процесса и индексируется `(window_start, merchant_category)`. Kafka распределяет события по `card_id`, поэтому одна категория в одну минуту может одновременно обрабатываться разными процессами. Каждый пишет свой частичный cumulative snapshot в общую Gold-таблицу. Serving выбирает последнюю строку для пары окно/категория и отбрасывает остальные через `drop_duplicates(..., keep="last")`.[^3][^4]

Контрпример по коду: первый processor обработал 6 событий категории, второй 4. Ожидаемый total равен 10, но `/stats` вернёт 6 или 4 в зависимости от времени последней записи. Это детерминированное следствие алгоритма, а не результат проведённого кластерного теста. Простое суммирование всех записанных snapshots тоже неверно, потому что они накопительные.

Нужна либо двухэтапная агрегация с repartition по ключу окна/категории, либо корректная схема частичных агрегатов с идентификатором partition и восстановлением progress, либо вычисление из дедуплицированного Silver. Отдельно требуется перенос/восстановление per-card state при rebalance. Оставление одной реплики временно избегает распределённой ошибки, но не выполняет требование масштабирования.

## 4. Корректность обработки и хранения

### P2. Restart теряет уже накопленное состояние

Consumer фиксирует offsets после трёх записей, что разумно для at-least-once на уровне обработки Kafka. Но `card_windows`, `latest_card_time` и `stats_state` создаются пустыми при каждом запуске. Уже закоммиченные события автоматически не восстанавливают состояние после restart.[^3]

Например, десять обычных платежей одной карты обработаны и offsets сохранены. После restart приходит одиннадцатый платёж в пределах 60 секунд. Вместо ожидаемого alert текущий процесс увидит только один платёж. Для category stats новый snapshot после restart может заменить более полный старый snapshot меньшим total. README признаёт потерю state при rebalance, но полезно явно описать и обычный restart с committed offsets.

### P2. Late data использует разные правила для velocity и category stats

Допустимое опоздание определяется относительно последнего события конкретной карты, а очистка `stats_state` — относительно глобального максимума времени. Поэтому событие новой карты может считаться допустимым, хотя его category window уже удалено из состояния.[^3]

Пример: после обработки актуальных событий приходит запись новой карты со временем на десять минут раньше. Для новой карты `is_too_late=False`; старое окно категории создаётся заново с total=1 и новым `updated_at`. `/stats` выберет эту неполную запись вместо исторического полного результата. Нужно согласовать watermark/allowed lateness с очисткой агрегатов либо обновлять сохранённый полный агрегат. Дополнительно README следует явно объяснить, что too-late записи исключаются и из `fraud_stats`, хотя остаются в Silver.

Ограничение, при котором допустимое late-событие не исправляет ранее выпущенные velocity snapshots, уже честно описано в README. Задание требует адресовать late data, но не предписывает конкретный watermark-алгоритм. Поэтому само это упрощение допустимо при ясном описании; проблема возникает там, где данные начинают ошибочно заменять полные агрегаты.

### P2. State не ограничен по числу неактивных карт

Очистка deque выполняется только при новом событии соответствующей карты. Ключи из `card_windows` и `latest_card_time` вообще не удаляются. Поэтому новые уникальные карты накапливаются в памяти бессрочно, даже если каждая совершила один платёж. Утверждение о bounded memory в README следует сузить: ограничен временной горизонт записей активной карты, но не общий объём состояния. Нужна глобальная очистка неактивных ключей с согласованной политикой lateness.[^3]

### P2. Producer не проверяет результат каждого Kafka send

`_publish` отбрасывает Future, возвращённый `producer.send`. Endpoint затем вызывает `flush` и возвращает `accepted=True`. В исходниках именно `kafka-python-ng v2.2.3` завершение flush допускает как успешное подтверждение, так и завершение отправки ошибкой. Следовательно, такой путь не гарантирует подтверждённую доставку конкретного платежа.[^2][^9]

Для одиночного платежа следует проверить Future через `get(timeout=...)` и возвращать ошибку API при неуспехе. Для генератора нужны обработка результатов отправок и итоговая статистика ошибок. Настройки retries также могут менять порядок batches при нескольких запросах in-flight; фраза о сохранении порядка должна отличать Kafka partition ordering от порядка первоначальных попыток отправки.[^9]

### P2. Explicit typed schema заявлена сильнее, чем реализована

`write_delta` создаёт `pd.DataFrame(rows)` и передаёт его в `write_deltalake` без явно заданной схемы. Временные поля записываются через `isoformat()`, то есть как строки. `schema_mode="merge"` разрешает эволюцию, но не задаёт исходные типы и nullable-контракт. README §6 в текущем виде неточен.[^3]

Можно либо ввести явную Arrow schema и определить типы всех колонок, либо честно описать выведение типов и отдельно привести таблицу фактических типов. Задание требует обоснования схемы, а не обязательно конкретной реализации через Arrow. Silver partitioning по `event_date` соответствует коду. Обе копии merchants CSV побайтово совпадают по SHA-256; текущего расхождения reference data не найдено.

### P2. Replay не создаёт чистую новую проекцию

README предлагает replay через новую consumer group/reset offsets. При неизменных путях таблиц код добавляет события в уже существующие Silver и Gold. Это ведёт к дублированию истории, а не к чистому пересозданию derived views. Для убедительного объяснения Kappa стоит описать replay в новые пути/новый bucket с последующим переключением serving либо безопасную дедупликацию. Отсутствие exactly-once допустимо, но инструкция replay должна соответствовать append-семантике.[^3]

## 5. Kubernetes, UI и доказательства

Workload-типы, ConfigMap/Secret, PVC, requests/limits, HPA и отдельная UI организованы последовательно. Для StatefulSet отсутствуют отдельные headless Services: текущие Services имеют обычный ClusterIP. Официальная документация Kubernetes связывает устойчивую сетевую идентичность StatefulSet с headless Service. Это замечание к полноте stateful-развёртывания, особенно при переходе к нескольким pod; оно не доказывает невозможность связи с единственным экземпляром через текущий Service.[^6][^10]

Processor readiness/liveness проверяет существование файла `/tmp/processor-ready`, создаваемого один раз после инициализации consumer. Такая проверка не замечает остановку прогресса живого процесса. Producer/serving health endpoints также не проверяют доступность зависимостей. Для учебного прототипа это допустимое упрощение, но подписи «healthy» должны опираться и на реальные outputs, а не только probes.

UI действительно имеет обе роли, хотя достаточно одной: отправку событий и просмотр результатов. nginx связывает её с реальными producer/serving endpoint; SSE имеет polling fallback. Dashboard и `/summary` на изображениях согласуются: 5 581 processed, 894 flagged, 0.1602 fraud rate. Это полезное доказательство предыдущего успешного прохождения данных.[^4][^5][^7]

`ui-producer.png` показывает заполненную форму и элементы генератора, но не видимый ответ accepted/scheduled. Лучше снять подтверждение действия и затем результат той же транзакции. `pipeline-output.png` показывает повторяющееся сообщение о flush, но не примеры Silver/Gold rows. Для более сильного доказательства стоит добавить конкретную запись с transaction_id, enrichment, flags и window output, а также пример late-event. Подмена этих материалов синтетическими скриншотами была бы недостоверной.

README содержит Mermaid, который не каждый офлайн Markdown viewer отрисует. Стоит встроить локальный PNG/SVG схемы рядом с исходным Mermaid, чтобы диаграмма была видна внутри ZIP без внешних ресурсов. Это рекомендация для переносимости доказательств, а не отдельное прямое требование формата изображения.

Бонус до +10 возможен за обоснованные отклонения и дополнительную полезную функциональность, но общий максимум остаётся 100. MinIO, собственный processor, SSE и CI дают основания для обсуждения бонуса; наличие конфигурационных файлов само по себе не гарантирует его.[^1]

Отсутствие ML, TLS, authentication, production HA, отдельного Bronze или exactly-once не следует представлять как самостоятельное нарушение задания. Эти улучшения надо отличать от прямо обязательной горизонтальной масштабируемости и понятного работающего потока.

## 7. Рекомендуемый порядок исправлений

1. Установить причину Error producer/processor, получить стабильный полный запуск и переснять cluster/UI/API evidence в одной сессии. Это самая быстрая возможность устранить прямое противоречие в сдаче.
2. Исправить распределённые category aggregates и определить восстановление per-card state. Проверить одинаковый результат при одном и нескольких processor.
3. Реализовать воспроизводимый scale-out вариант Kafka и MinIO; показать работу всех компонентов в нескольких экземплярах. Обновить README §8 и ограничения в §12 по фактическому состоянию.
4. Исправить late-window reset, проверку Kafka Future и очистку неактивных ключей. Согласовать описание schema/replay с реализацией.
5. Дополнить evidence конкретными input/output, late-data и scaling результатами. Исправить подписи изображений, ссылки на строки и локальное представление диаграммы.
6. Сформировать и проверить окончательный ZIP. Убедиться, что README, четыре сервиса, полный Helm chart, CSV и все изображения находятся внутри. Значимые сведения из этого аудита перенести в README.

## 8. Проверки, необходимые для закрытия замечаний

| Сценарий | Ожидаемый результат |
| --- | --- |
| Обычный, high-amount и high-risk merchant платежи | Каждая запись проходит UI → Kafka → Silver → API; flags соответствуют правилам. |
| 11 платежей одной карты за 60 секунд | На одиннадцатом возникает velocity alert. |
| Restart между десятым и одиннадцатым | Результат совпадает с непрерывным запуском после реализации восстановления. |
| Два processor, одна категория, разные карты/partitions | `/stats.total` равен сумме всех уникальных событий окна. |
| Опоздавшая запись новой карты в удалённое окно | Старый полный агрегат не заменяется строкой total=1. |
| Ошибка Kafka send | API не сообщает об успешной доставке события. |
| Долгий поток уникальных карт | Неактивные ключи освобождаются по документированной политике. |
| HPA/scale-out | Несколько ready pod, подтверждённая нагрузка и сохранение правильных результатов. |
| Чистая установка из ZIP | Образы собираются, chart разворачивается, UI работает по инструкции. |

Эти сценарии являются планом проверки, а не списком успешно выполненных тестов. В текущей среде нет доступных Python-интерпретатора, Docker, Helm и kubectl, поэтому Python unit tests, image builds, Helm rendering и запуск Kubernetes не выполнялись. Проверка синтаксиса `services/ui/html/app.js` через Node завершилась успешно. Выполнены чтение всех четырёх страниц задания, просмотр шести screenshots, проверка ключевого кода/манифестов/CI и сравнение CSV.

CI описывает Python syntax checks, восемь unit tests producer/processor, рендер двух Helm-режимов и сборку четырёх образов. Это полезно, но текущие тесты не покрывают live processing loop, restart, distributed aggregation, Delta round-trip или e2e UI. Наличие workflow не подтверждает успешное прохождение конкретного запуска CI.[^8]

`git archive HEAD` не включает незакоммиченные файлы и `.git`. При необходимости подтвердить историю без внешних ссылок можно добавить краткую выдержку значимых commits в README. Для итоговых функциональных исправлений сначала нужно убедиться, что они включены в архивируемую версию; текущие различия только по концам строк не меняют выводов проверки.
