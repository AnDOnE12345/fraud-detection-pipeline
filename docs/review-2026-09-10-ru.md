## Что исправить в README

1. **Вступление и §11: обновить статус v2.** Указать успешный локальный запуск 10.09.2026 в `fraud-lab`; отдельно сохранить отсутствие распределённого scale demo. Не переносить исторические 5 581 / 894 на новый запуск.

   Возможная точная формулировка:

   > The v2 implementation was verified in the local `fraud-lab` Kubernetes deployment on 2026-09-10. All seven pods were ready in the captured snapshot. Serving reported 220 processed and 31 flagged payments (14.09%), with velocity alerts for counts 11 through 15. All 22 Python tests passed. The distributed scale profile has not yet been verified in a live deployment.

2. **§11: заменить основные исторические изображения свежими.** Нужны UI с принятым платежом и его результатом, `kubectl get pods`, serving output и пример processor output. Для каждого снимка написать, какой сценарий он подтверждает. Исторические скриншоты можно убрать из основного доказательства либо оставить отдельно с датой; нельзя выдавать их за текущую версию.

3. **§8 и §11: сохранить честный статус масштабирования и добавить результаты после демонстрации.** В PDF на стр. 2 требуется проектирование и показ горизонтального масштабирования всех компонентов. Одна таблица HPA или две serving replicas закрывают только часть. Scale profile предусматривает 3 Kafka, 4 MinIO и несколько экземпляров приложений. Его суммарные memory requests составляют 5632 MiB, без системных pod, поэтому Minikube с 3000 MB не сможет разместить этот профиль. Нужна среда с большим ресурсом; README уже приводит 12 GB / 8 CPU как ориентир. Переход standalone MinIO в distributed in-place не делать: использовать новый namespace/PVC, как в существующей инструкции.

4. **§9: дать полный Windows/PowerShell quick-start для `fraud-lab` перед scale-инструкцией.** Docker Desktop должен быть запущен. Фактически использованная локальная конфигурация — `minikube start --driver=docker --cpus=4 --memory=3000`; это не гарантированный минимум. Указать сборку четырёх образов, image load, Helm install, ожидание готовности и port-forward; пояснить, что терминал port-forward остаётся открытым.

5. **§9: описать обновление образов и конфигурации.** Пересборка того же `:dev` не обновляет работающий Deployment автоматически. Предпочтителен новый тег с image load и обновлением `images.*` через Helm, затем `rollout status`. Если используется прежний тег, нужны загрузка нового образа и явный restart. Сейчас producer в кластере использует `local/fraud-producer:readiness-fix`, а chart по умолчанию указывает `:dev`; перед следующей установкой нужно пересобрать `:dev` из исправленного кода либо явно указать новый тег в Helm.

6. **§9, Migration and replay: учесть применение ConfigMap.** Изменение `storage.prefix`/consumer group меняет ConfigMap, но текущие pod читают env только при старте; checksum ConfigMap в pod template нет. Нужен согласованный перезапуск processor и serving, с переключением serving после catch-up нового prefix. Аналогично обновление thresholds требует перезапуска затронутых сервисов. Либо это следует автоматизировать в chart — одной правки описания недостаточно для автоматического применения env.

7. **§8: уточнить readiness producer.** Теперь проверяется доступность topic partition metadata через `partitions_for`, а каждая отправка отдельно ожидает broker acknowledgement. Формулировка `checks its Kafka connection` неточна: cached metadata не доказывает непрерывное живое соединение. Это исправление убрало ложное снятие готовности после закрытия bootstrap connection и ошибку 502.

8. **§11: 19 tests → 22 tests.** Указать producer 9, processor 10, serving 3. Старую проверку Helm отделить от текущего прогона; не заявлять новый успешный полный CI без результата запуска.

9. **§8–9: уточнить KEDA.** Два processor в scale profile относятся к режиму без KEDA. При `keda.enabled=true` минимальное количество по текущим defaults — 1; для двух требуется `--set keda.processor.minReplicaCount=2`.

10. **§11: добавить воспроизводимые сценарии input → output.** Уже можно подтвердить обычный платёж, flagged payment и velocity burst текущими данными. Перед заявлением live recovery/late-data результатов нужны реальные снимки до/после рестарта и запросы с event_time. Unit tests подтверждают алгоритм, но не заменяют такие скриншоты.

## Дополнительная проблема воспроизводимости

Команда `./scripts/capture-evidence.ps1 -Namespace fraud-lab` в Windows PowerShell остановилась на информационном stderr от `kubectl logs`: выбран контейнер `processor` среди основного и init-контейнера. При `$ErrorActionPreference = 'Stop'` это превратилось в ошибку скрипта до проверки exit code.

В `scripts/capture-evidence.ps1` для processor logs следует явно задать `-c processor` и корректно различать ненулевой exit code и информационный stderr. Во время аудита данные сохранены отдельными командами с явным контейнером. Исходный скрипт в рамках аудита не изменён.
